UX-CK-01 Sidebar Navigation Entry

Add "Launch Checklist" to the NavigationDrawer with rocket icon, positioned after "Business Case" in the module flow.

Overview

The Launch Checklist is Module 3 in the UX-D hub model. It must appear in NavigationDrawer.svelte with:

  • Label: "Launch Checklist"
  • Short label: "Checklist" (for mobile truncation)
  • Icon: Rocket emoji or SVG icon (🚀)
  • Path: /app/checklist
  • Unlock state: Available after Business Case visited

Implementation Details

  • Module 3 label = "Launch Checklist" (currently correct)
  • Lock state: locked: false (always unlocked, but next: true only after Business Case)
  • Icon renders as rocket emoji in module list
  • Active state highlights when /app/checklist is current path
  • Disabled state shows "Coming soon" if Business Case not yet visited

Visual States

  • Available: Normal text, blue underline on hover
  • Active: Bold text, blue background or left border highlight
  • Done: Green checkmark next to label

Acceptance Criteria

  2. Rocket icon (🚀) renders before label text
  3. Disabled state shows if Business Case not visited
  4. Active state highlights when user is on /app/checklist

  6. Clicking navigates to /app/checklist (no console errors)

UX-CK-02 Responsive Layout (Mobile / 768px)

All components adapt gracefully on screens ≤768px (iPad, tablet, mobile). Layout should be tested at 375px, 768px, and 1024px breakpoints.

Breakpoint Strategy

  • Mobile (≤375px): Full-width single column, font sizing reduced 10%
  • Tablet (376–768px): 2-column grids where applicable, sticky headers
  • Desktop (>768px): 4-column grids, full spacing

Component-Level Breakpoints

ChecklistProgress (Progress Bar)

  • Desktop: Horizontal layout with stats on right
  • Tablet (≤768px): Stack vertically; phase dots scroll horizontally
  • Phase dots: Always visible, scroll if overflow

ChecklistFilters (Filter Chips)

  • Desktop: Grid of filter chips, wrapping allowed
  • Tablet: Horizontal scroll container, snap to edges
  • Chip size: Reduce padding 2px on mobile
  • Badge count: Always visible (no hiding on mobile)

ChecklistPhase (Phase Headers)

  • Remain sticky on all breakpoints (position: sticky; top: 0)
  • Z-index: 10 to layer above task cards
  • Font size: 16px desktop, 14px mobile

ChecklistItem (Task Cards)

  • Desktop: Flex layout with checkbox, body, Find a Pro, cost badge
  • Tablet: Flex direction row, cost badge on right
  • Mobile: Stack Find a Pro button above cost badge (or hide button if space limited)
  • Notes textarea: Full width on all breakpoints

ChecklistCostSummary (Summary Cards)

  • Desktop: 4-column grid
  • Tablet: 2-column grid
  • Mobile: 1-column stack
  • Card padding: 16px on mobile, 20px on tablet+

Navigation & Spacing

  • Content padding: 32px desktop, 16px tablet, 14px mobile
  • PageNav buttons: Full width on mobile (≤375px)
  • No-session warning: Adjust padding for small screens
/* Example: ChecklistCostSummary responsive grid */ @media (max-width: 768px) { .cost-grid { grid-template-columns: repeat(2, 1fr); } } @media (max-width: 480px) { .cost-grid { grid-template-columns: 1fr; } }

Acceptance Criteria

  1. All components stack vertically on mobile (375px)
  2. Filter chips horizontally scroll on tablet/mobile
  3. Phase headers remain sticky on all breakpoints
  4. Cost summary cards: 4-col desktop → 2-col tablet → 1-col mobile
  5. Task cards remain readable with checkbox, name, meta visible
  6. Find a Pro button behavior: visible desktop, hidden mobile (or layout adjusted)
  7. Notes textarea full width on all breakpoints
  8. No horizontal scrolling at 375px (except intentional chip scroll)
  9. All text remains readable (min 12px font on mobile)

UX-CK-03 Print Stylesheet

Print view should show all tasks expanded with notes inline, no navigation or buttons, optimized for 8.5" x 11" paper.

Elements to Hide

  • NavigationDrawer (sidebar)
  • PageNav (back/next buttons)
  • ChecklistProgress (progress bar header)
  • ChecklistFilters (filter chip row)
  • Find a Pro button
  • MarketplaceBanner
  • Checklist no-session warning
  • Cost summary cards (optional: can show as final summary)

Elements to Show / Modify

  • All ChecklistPhase headers: bold, black text on white
  • All ChecklistItem cards: expanded by default, borders visible
  • Task notes: inline, no textarea styling, regular text
  • Checkboxes: print as [✓] or [ ] (checked/unchecked)
  • Cost badges: visible next to task name
  • Priority labels: print in color or as text (e.g., "[DO NOW]")

Page Break Rules

  • page-break-inside: avoid on .task cards (prevent mid-card breaks)
  • page-break-inside: avoid on ChecklistPhase sections
  • Allow breaks between phases if needed
  • Margins: 0.5" on all sides
@media print { .cl-page { background: #fff; } .navigation-drawer, .page-nav, .checklist-progress, .checklist-filters, .find-pro, .marketplace-banner, .cl-no-session { display: none !important; } .task { page-break-inside: avoid; border: 1px solid #000; } .task-check { border: 1px solid #000; } .task-check.checked::after { content: '✓'; } .cost-grid { display: none; } /* or: display: grid; for summary footer */ body { font-size: 11pt; line-height: 1.5; } .task-name { font-weight: bold; } }

Acceptance Criteria

  1. Print preview hides all navigation elements (drawer, PageNav, etc.)
  2. All task cards print with no page breaks mid-card
  3. Task notes appear inline (not in textarea)
  4. Checkboxes print as [ ] or [✓]
  5. Cost and priority labels visible in print
  6. Document fits on standard 8.5x11" pages (no overflow)
  7. Print to PDF produces clean, readable output
  8. No color dependencies (works in grayscale too)

UX-CK-05 Session/Store Handoff

Verify the checklist page correctly reads and persists context (location, concept) from localStorage and Supabase. Test navigation flows to ensure no data loss.

Storage Keys & Format

  • re2_launchpad: { conceptType: 'specialty_coffee', conceptLabel: 'Specialty Coffee' }
  • re2_session: { analyzedAddress, neighborhood, locationIQ, geoid, ... }
  • re2_checklist: { items: [{ id, done, notes }, ...] }
  • re2_checklist_visited: 'true' (marks checklist as completed)

Initialization on Mount

File: src/routes/app/checklist/+page.svelte

Current implementation (onMount):

  1. Read conceptType from re2_launchpad (default: 'specialty_coffee')
  2. Load item template via getItemsForConcept(conceptKey)
  3. Restore done/notes from re2_checklist
  4. Read location/concept labels from re2_session + re2_launchpad
  5. Mark page visited: re2_checklist_visited = 'true'

Verify: All keys parse correctly with try/catch; no unhandled exceptions on corrupt JSON.

Persistence on Change

Debounced save (300ms) on any item toggle/note update:

  • Save to localStorage (primary)
  • Sync to Supabase via /api/checklist-sync (secondary, non-blocking)
  • locationId extracted from geoid or analyzedAddress
  • Payload: { locationId, items: [{ itemId, done, notes }, ...] }
  • Silent fail if API error (localStorage already saved)

Navigation Test Cases

Scenario 1: BC → Checklist → BC

  • Start on Business Case page, mark items as done
  • Navigate to Checklist (via PageNav or sidebar)
  • Toggle a few tasks, add notes
  • Back to Business Case (PageNav), then forward to Checklist
  • Expected: All checked items and notes persist (no loss)

Scenario 2: Checklist → Dashboard → back

  • Mark all tasks complete, add notes to 2–3 items
  • Navigate to Dashboard
  • Back to Checklist (browser back button)
  • Expected: All state restored; no blank/lost items

Scenario 3: Multi-tab session

  • Open Checklist in Tab A, mark item 1 done
  • In Tab B, open same location, open Checklist
  • Mark item 2 done in Tab B, refresh Tab A
  • Expected: Tab A reflects changes (or shows stale data with refresh note)

No-Session Handling

  • If locationIQ = 0, show nudge banner: "You haven't analyzed a location yet."
  • Banner includes link to /app/location
  • Checklist items still load (default concept), but full context unavailable
  • No auto-redirect (let user decide)

Acceptance Criteria

  1. Checklist loads correct concept (specialty coffee by default)
  2. Location name/concept label populate from session
  3. Checked items and notes restore from localStorage on reload
  4. Sync to Supabase succeeds without blocking UI
  5. Navigation (BC → CL → BC) preserves all state
  6. No data loss on back/forward navigation
  7. No-session banner shows if location not analyzed
  8. Corrupt localStorage JSON does not crash page (try/catch handles)
  9. Multiple concepts show different item sets (verify with concept switch)

UX-CK-07 Filter Chip Count Badges

Display count badges on all filter chips (All, To Do, Done, Now, Soon, Later) showing the number of matching tasks. Active chip uses navy background + white text.

Badge Display

File: src/lib/components/checklist/ChecklistFilters.svelte

  • All chip: Count of all items in current concept
  • To Do chip: Count of items where done === false
  • Done chip: Count of items where done === true
  • Now chip: Count of items where priority === 'now'
  • Soon chip: Count of items where priority === 'soon'
  • Later chip: Count of items where priority === 'later'

Badge Styling

  • Position: Inline or top-right corner of chip (floating badge style)
  • Background: Inherit from chip (or #fff on colored backgrounds)
  • Size: 16–20px diameter (small circle or rounded pill)
  • Font: 10px, font-weight: 700, centered text
  • Padding: 2px (circle) or 2px 6px (pill)
  • Zero counts: Show "0" (do not hide)

Active Chip State

  • Background: #1a3a52 (navy) or #1B4965 (darker blue)
  • Text color: #fff (white)
  • Border: None (or 1px solid #1a3a52)
  • Badge on active chip: Show count in white on navy (high contrast)

Chip Layout Example

Chip: "All" ├─ Text: "All" └─ Badge: "51" (circle, top-right) Active Chip: "To Do" (navy background) ├─ Text: "To Do" (white) └─ Badge: "23" (white text on navy circle)

Badge Count Logic

All counts are recalculated on item state change (toggle done, change priority).

  • Counts reflect real-time state (no lag)
  • Counts reset if filter applied (show filtered count)
  • Example: If 51 total items, 23 to-do, 28 done → badges show [51] [23] [28]

Acceptance Criteria

  1. All filter chips display count badges
  2. "All" badge shows total item count
  3. "To Do" badge shows count of unchecked items
  4. "Done" badge shows count of checked items
  5. "Now" / "Soon" / "Later" badges show counts per priority
  6. Active chip background is navy (#1a3a52 or #1B4965)
  7. Active chip text is white
  8. Badge on active chip is visible (white text on navy)
  9. Counts update instantly when item toggled
  10. Counts show "0" if no items match filter
  11. Badge positioning is consistent across all chips
  12. No layout shift when count changes (1–3 digits)
